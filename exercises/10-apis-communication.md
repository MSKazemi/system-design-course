### 1. [Core] Which retries are safe?

A mobile client loses its connection after sending each of these requests and does not know whether the server
processed it. Which may a client library or mesh retry automatically, and why?
(a) `GET /v1/documents/42` (b) `PUT /v1/documents/42` with the full document (c) `DELETE /v1/documents/42`
(d) `POST /v1/chat/completions` (e) `PATCH /v1/documents/42` with `{"views": "+1"}`

<details><summary>Answer</summary>

RFC 9110 defines a method as idempotent if repeating the identical request has the same intended effect as sending it
once; PUT, DELETE and the safe methods are idempotent [2]. So:

- (a) GET: safe and idempotent → retry.
- (b) PUT of a full representation: idempotent → retry. Sending the same full document twice leaves the same state.
- (c) DELETE: idempotent → retry. The second call may return 404 instead of 204, but the *state* is the same. Clients
  must treat "already gone" as success.
- (d) POST: not idempotent → **do not** retry blindly. A retry could create and bill a second completion. Make it safe
  with an `Idempotency-Key` [18].
- (e) PATCH: not idempotent by definition (RFC 5789 [34]), and this one is plainly non-idempotent because "+1"
  increments each time. Rewrite it as an idempotent operation (a PUT of the new absolute value with an `If-Match`
  ETag), or attach an idempotency key.

Acceptable alternative: some PATCH requests are idempotent in practice (setting a field to an absolute value), but a
generic library cannot know that, so it must not retry them automatically.
</details>

### 2. [Core] The boundary burst

Policy: 10 requests per 60 s per key. A client sends 10 requests at t = 59.9 s and 10 more at t = 60.0 s; windows
start at multiples of 60 s. How many of the 20 does each algorithm admit? (a) fixed window (b) sliding window log
(c) sliding window counter (d) token bucket, capacity 10, refill 10/60 per second, full at t = 59.9 s.

<details><summary>Answer</summary>

- (a) **Fixed window: 20.** The first 10 fill window [0, 60); at 60.0 s a new window starts with a zero counter, so
  the next 10 also pass. Twice the limit in 0.1 s.
- (b) **Sliding window log: 10.** At 60.0 s the log still holds 10 timestamps from 59.9 s (within the last 60 s).
- (c) **Sliding window counter: 10.** At 60.0 s, elapsed = 0, so the estimate is `prev × (60 − 0)/60 + cur = 10`;
  no capacity remains.
- (d) **Token bucket: 10.** The burst empties the bucket; 0.1 s later only about 0.017 tokens have been added.

Lab L10 Experiment 1 runs exactly this scenario (with a 10 s window) and shows the fixed window admitting 20.
</details>

### 3. [Core] SSE or WebSockets?

For each feature pick SSE, WebSockets, long polling or gRPC streaming, and justify it:
(a) streaming an LLM answer to a browser; (b) a shared document with live cursors; (c) the chat service consuming
tokens from the internal inference router; (d) a status page that changes a few times per hour.

<details><summary>Answer</summary>

- (a) **SSE.** One direction (server → client), plain HTTP that gateways and proxies already handle, built-in
  reconnection with `Last-Event-ID` [10]. Both major commercial LLM APIs stream over SSE [12][13].
- (b) **WebSockets.** Many small messages in both directions with low latency; a two-way channel avoids opening a
  request per cursor movement [11].
- (c) **gRPC server streaming.** Internal, typed, deadline-aware, multiplexed on HTTP/2 [5].
- (d) **Polling** (or long polling). Updates are rare; a cacheable GET every 30–60 s is simplest, and CDN caching
  absorbs the load.

Acceptable: SSE for (d) is fine too, but holding a connection open per viewer to deliver a few events per hour
wastes connection capacity.
</details>

### 4. [Core] Design the idempotent endpoint

Design `POST /v1/charges` so that client retries never double-charge. Specify: where the key comes from, what you
store, the transaction boundaries, and the responses for (i) a retry after success, (ii) a retry while the first
request is still running, (iii) a retry with the same key but a different amount.

<details><summary>Answer</summary>

- **Key:** generated by the client per logical operation (a UUID), sent as `Idempotency-Key` [18]. Scope it per tenant.
- **Store:** table `idempotency_keys(tenant_id, key, request_hash, status, response_code, response_body, locked_at,
  created_at)` with a unique index on `(tenant_id, key)` [20].
- **Flow:** insert the key row (status `in_progress`); the unique constraint makes concurrent duplicates fail. Perform
  the charge and update the key row with the response **in the same database transaction** if the charge is local.
  If the charge goes to an external processor, pass a derived key downstream so the processor de-duplicates too, and
  record recovery points between steps [20].
- **(i)** Replay the stored status and body (e.g. the original 201) without doing any work [19].
- **(ii)** 409 Conflict; the client retries later [18][20].
- **(iii)** 422 because the payload fingerprint does not match the stored hash [18].
- **Expiry:** publish it (e.g. 24 h, the minimum Stripe documents for its v1 API [19]); after expiry the key is treated
  as new.
</details>

### 5. [Interview] Design a distributed rate limiter

"Lumen's gateway has 30 replicas and must enforce 100 requests/minute per API key across all of them, with < 2 ms
added at p99. There are 3 million API keys and a peak of 60,000 requests/s." Walk through CLARIFY → QUANTIFY →
SKETCH → DEEPEN → STRESS → WRAP in about 10 bullet points.

<details><summary>Answer</summary>

1. **CLARIFY:** key = API key (also a per-tenant limit?); unit = requests; are bursts allowed? hard or soft? behavior
   on limiter failure? which headers do clients get?
2. **QUANTIFY:** 60k checks/s → 60k Redis script calls/s if done per request. With an assumed 25k calls/s per primary
   (measure it), 3 primaries minimum, 4–6 with headroom. Memory with a sliding window counter: 3 M keys × 2 counters ×
   ~46 B ≈ 0.3 GB (lab L10 measured 46 B per counter key with `MEMORY USAGE` on Redis 8.10.3; add replica and
   allocator overhead).
3. **SKETCH:** gateway → local token bucket (coarse, in memory) → Redis Cluster sharded by API key, one Lua script per
   check → allow, or 429 with `Retry-After` [21] and `RateLimit` fields [28].
4. **DEEPEN — algorithm:** token bucket (allows short bursts, matches "per minute" averages) or sliding window counter
   (users understand "100 per minute"); reject the fixed window because of the 2× boundary burst.
5. **DEEPEN — atomicity:** the read-check-write runs as one Lua script; Redis executes scripts atomically [25]. Keys
   passed in `KEYS` for cluster safety.
6. **DEEPEN — clock:** pass a disciplined gateway clock or read Redis `TIME` inside the script [25].
7. **STRESS — store down:** fail open for cheap reads (Stripe's advice [22]), fail closed or fall back to a strict local
   bucket for expensive endpoints (GPU inference).
8. **STRESS — hot key:** one key at 20k req/s → split into sub-keys or use quota leasing.
9. **STRESS — multi-region:** per-region limits (limit/regions) or a global budget synced periodically; accept
   approximation.
10. **WRAP:** summarize; monitor 429 rate per key, limiter p99 latency, store error rate; dark-launch new rules [22].

Red flags: no failure policy, application-level read-then-write, a single Redis instance for everything.
</details>

### 6. [Deep] Token bucket for LLM tokens

A tenant's policy is 40,000 LLM tokens per minute. You do not know how many tokens an answer will contain until it
finishes. Design the admission check.

<details><summary>Answer</summary>

Use a token bucket with variable cost: refill rate 40,000/60 ≈ 667 tokens/s, capacity e.g. 40,000 (allowing one
minute's burst — a product decision). On admission, **reserve** `prompt_tokens + max_tokens` (the worst case the
request may consume); deny with 429 and a `Retry-After` computed from the deficit / refill rate if the bucket lacks
them. When the stream ends, **refund** `max_tokens − completion_tokens`. If the client disconnects mid-stream, the
server stops generating (cancellation) and refunds the remainder.

Trade-offs: reservations make limits conservative — a tenant sending `max_tokens = 8,000` for 200-token answers is
throttled early, which is a good incentive to set realistic `max_tokens`. The alternative (charge actual usage after
the fact and let the balance go negative) admits more but lets one burst overshoot the budget. Both are used; state
which one you chose. The lab's token bucket script already takes a `cost` argument.
</details>

### 7. [Deep] Evolve a protobuf message

```proto
message Document {
  string id = 1;
  string title = 2;
  int32 size_kb = 3;
  string owner_email = 4;
}
```

You must (a) stop exposing `owner_email` (privacy), (b) change `size_kb` to bytes with 64-bit range, (c) add a
`tags` list. Old mobile clients will stay in the field for a year. Write the new message and explain each step.

<details><summary>Answer</summary>

```proto
message Document {
  reserved 4;
  reserved "owner_email";
  string id = 1;
  string title = 2;
  int32 size_kb = 3 [deprecated = true];   // keep populating for old clients until retired
  int64 size_bytes = 5;                     // new field, new number
  repeated string tags = 6;                 // additive
}
```

- (a) Deleting a field is safe only if its **number and name are reserved**, so no one reuses them and JSON/text
  parsing keeps working [32]. Old clients simply see the field as absent (empty string default), so check that they
  handle that.
- (b) Changing `int32` to `int64` in place is *wire*-compatible [32], but it is a *meaning* change (KB → bytes), and
  AIP-180 treats type changes as breaking because generated code changes [33]. Add a new field with a new number,
  populate both during the migration, then retire the old one.
- (c) Adding a field is safe; old code ignores unknown fields [32].
- New fields use 5 and 6, which still encode in one byte (1–15) [32].
</details>

### 8. [Core] Pagination at depth

An admin UI lists audit events (1 billion rows, newest first) with `?page=N&size=50`. Page 20,000 takes 9 s and
users report seeing duplicate events while paging. Explain both symptoms and redesign the endpoint.

<details><summary>Answer</summary>

`OFFSET 999,950 LIMIT 50` makes the database produce and discard ~1 million rows before returning 50 — work grows with
depth [17]. New events inserted at the head between requests shift every row down, so the next page repeats items
already seen [17].

Redesign with keyset pagination: sort by `(created_at DESC, id DESC)` with a matching index; return
`next_page_token` = opaque, URL-safe encoding of the last `(created_at, id)`; the next query is `WHERE (created_at,
id) < (:c, :i) ORDER BY created_at DESC, id DESC LIMIT 50`. Follow AIP-158: optional `page_size` with a documented
max, an empty `next_page_token` as the only end signal, an optional estimated `total_size`, and tokens that are not
user-parseable [16]. For "jump to date", add a filter parameter (`before=2026-11-01`) rather than page numbers.
</details>

### 9. [Deep] Fail open or fail closed?

The Redis cluster behind the rate limiter becomes unreachable for 3 minutes. For each endpoint decide fail open,
fail closed or local fallback: (a) `GET /v1/documents/{id}`; (b) `POST /v1/chat/completions` (GPU inference);
(c) `POST /v1/auth/login`; (d) `POST /v1/webhooks/test`.

<details><summary>Answer</summary>

- (a) **Fail open.** Cheap, cached, read-only; an outage of the limiter should not become an outage of the API —
  Stripe's stated default [22].
- (b) **Local fallback** (a conservative per-gateway token bucket, e.g. limit / number of replicas) or fail closed.
  Unlimited GPU work for 3 minutes can cost real money and push inference into overload.
- (c) **Fail closed or strict local fallback.** Login limits defend against credential stuffing; removing them is a
  security regression.
- (d) **Fail closed.** Low value, and abusable for outbound traffic amplification.

Whatever you choose: alert on limiter errors, keep per-rule kill switches, and record the decision per endpoint.
</details>

### 10. [Lab] Read the race

In lab L10 Experiment 4 (recorded run, 2026-11-20), the naive token bucket admitted all 50 of 50 clients in each of
three trials against a capacity of 10, while the Lua version admitted exactly 10 each time. Explain why, and name two other ways to make the naive version
correct.

<details><summary>Answer</summary>

The naive version reads the bucket (`HMGET`), decides in Python, then writes (`HSET`) — two round trips. When 50
clients pass the barrier together, most of them read the same "full bucket" state before any write lands, so each
believes a token is available, and the last writer wins. The Lua version runs read, decide and write inside Redis
as one atomic unit; Redis blocks other commands while a script runs [25], so each client sees the effect of the
previous one.

Alternatives: (1) optimistic concurrency with `WATCH`/`MULTI`/`EXEC`, retrying on conflict (correct, but contention
causes many retries exactly when load is high); (2) restructure the algorithm around single atomic commands (e.g. a
fixed or sliding window built on `INCR`, or a GCRA stored with one conditional `SET`), or move the script into a
Redis Function.
</details>

### 11. [Interview] REST, gRPC or GraphQL?

Lumen has a public partner API, 40 internal services, and three first-party front ends (web, iOS, Android) whose
screens each combine data from 4–6 services. Propose the protocol per boundary in three sentences and defend one
trade-off.

<details><summary>Answer</summary>

Public partner API: REST/JSON with OpenAPI, SSE for streaming, date-based versioning with a published support window
(like GitHub's ≥ 24 months [15]). Internal services: gRPC with protobuf, deadlines and additive-only schema evolution
[5][32]. First-party front ends: optionally a GraphQL aggregation layer (or per-client back ends) so each screen
fetches exactly what it needs in one round trip.

Trade-off to defend: GraphQL moves cost control and authorization to the server — we must batch resolvers
(DataLoader [8]) and rate-limit by query cost like GitHub's points model [9], not by request count. If the team cannot
run that safely, per-client REST aggregation endpoints are the simpler alternative.
</details>
